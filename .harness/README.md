# Lightweight Project Harness

本目录用于保存能够跨会话、工作树和开发工具延续的项目记忆。本协议只定义通用工作方式；产品规则、技术约束、验证命令和版本控制收尾策略由具体项目另行规定。

## 文档职责

- `spec/SPEC.md`：项目长期有效的事实与约束，是需求、设计和验收标准的主入口。
- `STATUS.md`：项目当前状态的低频快照，只保留当前阶段、主要任务、下一步、阻塞项和最近完成事项。
- `tasks/active/`：需要跨会话、跨模块或明确验收边界的当前任务胶囊。
- `tasks/archive/`：已完成或取消的重要任务记录，用于保留范围、取舍和验证结果。

`tasks/active/` 和 `tasks/archive/` 在没有内容时可以不存在，不使用占位文件强行保留空目录。

## 读取顺序

开始项目任务前，按以下顺序建立上下文：

1. 读取当前工具或项目提供的适配指令。
2. 阅读 `spec/SPEC.md`，确认长期约束和项目定义的风险、验证要求。
3. 阅读 `STATUS.md`，确认当前阶段、优先事项和阻塞项。
4. 如果 `tasks/active/` 中存在任务胶囊，阅读其范围、验收标准和下一步。

发现文件之间冲突时，先确认冲突属于长期规范、当前状态还是单次任务，不得静默选择其中一个继续执行。

## 何时创建任务胶囊

小型、明确、可在单次工作中完成且验收方式清晰的局部修改，不创建任务胶囊。

满足以下任一条件时，应在 `tasks/active/` 创建任务胶囊：

- 工作可能跨越多个会话。
- 影响多个功能模块或技术层次。
- 存在需要明确记录的方案取舍。
- 包含多个验收点或回归风险。
- 按项目规范属于较高风险改动。

默认同时只维护一个主要 active task。任务文件使用 `YYYY-MM-DD-short-slug.md` 命名；`short-slug` 使用简短、稳定的 kebab-case 描述。

## 工作生命周期

1. 明确目标、范围、不在范围内的内容及验收标准。
2. 按项目规范判断风险；需要时创建任务胶囊并在 STATUS 中链接。
3. 实施过程中，仅在范围、验收条件、阻塞原因或跨会话下一步发生实质变化时更新任务胶囊。
4. 执行项目规定的自动验证和人工验收；未完成必需验收时，将任务标记为“待验收”。
5. 将长期有效的新事实同步到 SPEC，不把临时实现过程写入 SPEC。
6. 验收完成后填写验证结果，将任务从 `active/` 移至 `archive/`，并更新 STATUS。
7. 按项目定义的版本控制策略完成收尾。

完成或取消的任务都不得继续留在 `active/`。归档文档应说明最终结果；取消任务还应简述取消原因。

## 更新频率

- STATUS 只在任务启动、完成、阻塞或优先级发生实质变化时更新。
- “下一步”只保留少量可执行事项，“最近完成”只保留少量近期结果。
- 不记录逐文件操作、逐条命令、对话摘要、模型思考过程或可以由版本历史直接恢复的流水。
- 任务胶囊不要求每完成一个实现步骤就更新；其目标是支持决策、验收和跨会话续接。

## 版本控制与安全

- `.harness/` 中的协议、规范、状态、活动任务和归档属于项目记忆，应纳入版本控制。
- 不通过忽略 STATUS 或活动任务来减少差异；应通过低频、简洁的更新控制噪声。
- 只有实际引入的生成缓存、临时文件或日志才应被精确忽略，不得整体忽略 `.harness/`。
- 禁止写入密钥、密码、访问令牌、个人隐私、模型思考过程或仅在单台机器成立的临时信息。

## 任务胶囊模板

```markdown
# <任务标题>

- 状态：计划中 / 进行中 / 待验收 / 阻塞
- 创建日期：YYYY-MM-DD
- 风险等级：按项目规范填写

## 目标与背景

## 范围

## 不在范围内

## 验收标准

## 实施步骤

## 验证结果
```
